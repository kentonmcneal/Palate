## Findings and next bounded work

**1. Correct the consent story before presenting it as a trustworthy journey.** `mobile/app/onboarding/why-location.tsx:23` says location is used only while the app is open, but permission.tsx:30 offers the optional background introduction. `passive-capture-intro.tsx:182` says location never leaves the phone before confirmation. The actual pre-confirmation resolver passes stop coordinates to restaurantsNear and, if needed, nearbyRestaurantsDetailed (`lib/passive-pipeline.ts:607–658`). `lib/passive-inbox-sync.ts:53–100` mirrors venue identity/address and detection metadata before confirmation. Its exclusion of stopLat/stopLng is valuable but does not make the broader promise true. This is a source-level contradiction, not evidence that a particular person's data was transmitted.

Proposed cohesive wording: “Use your location to find nearby places. You can separately choose background visit suggestions. Palate may use a stop's location to identify a place and sync suggested stops to your account. You confirm a suggestion before it becomes a diary visit.” Keep technical storage details in an expandable explanation; obtain product/privacy review for the final disclosure. Do not replace the promise with another unverified assertion about retention or third parties.

**2. Intro completion still overstates startup.** `passive-capture-intro.tsx:50–61` proceeds to done after false startup outcomes; only native-module-unavailable gets a special alert. “You're set” and future “we'll ask” are stronger than those results establish. The new Settings component distinguishes saved consent, phone permission and temporary availability, but the intro must use the same distinctions. Show saved preference separately from “background checks did not start”; provide relevant repair/retry and Continue without capture. Never auto-enable on return. Darwin owns helper races; this audit proposes a later intro-only integration against his final contract.

**3. The nightly review can turn read failure into an empty day.** `app/digest.tsx:56` uses legacy getInbox; `lib/passive-confirm.ts:252–255` converts read exceptions to []. The page then says “Nothing captured today” (:185). The explicit getInboxReadResult API now present in the working source should be reused in a separate digest patch, with retry and preserved prior rows disabled while status is uncertain. Verified empty and unavailable must remain distinct. Current passive-inbox display recovery does not automatically fix this caller.

**4. Digest completion and admission need a screen-specific safety pass.** `digest.tsx:97–145` has React saving state but no synchronous admission slot or account/lifetime operation identity. A successful all-skipped response has no saved IDs and no failures; setDone(true) still shows “Logged” (:162). That conclusion follows directly from the branch; it was not newly reproduced with a mounted digest in this audit. Partial failures leave the old digest on screen, including previously successful rows. The helper tests establish preservation on failed saves, not safe repeated screen submissions. Proposed outcomes: “Saved 2 visits”, “Suggestions cleared” for all skipped, and “1 visit still needs saving” with only outstanding actionable rows. Add mounted same-turn repeats, stale account/focus responses, partial retry and all-skipped controls before implementing. Do not infer duplicate database rows merely from repeated callback admission.

**5. Confirmation → diary copy promises automatic logging that the flow does not provide.** `app/(tabs)/visits.tsx:127` and the owner's empty ProfileBody say visits collect themselves. Settings around :267 says the user never has to think about background logging. Replace with “Palate can suggest stops. Confirm the ones you visited, or add a visit yourself.” “Visit” includes coffee better than “meal”. Diary already provides an explicit load-error/retry for history, but its pending-inbox count uses the forgiving read and can disappear on failure. Its focus loader has no request/account cleanup. Single-confirm handlers in confirm-visit.tsx similarly rely on busy state, with delayed navigation and no screen operation identity. These are separate bounded follow-ups, not changes to the accepted saveVisit safeguards.
