3. [Context-window accounting](https://platform.claude.com/docs/en/build-with-claude/context-windows): system/message/cached input and generated output occupy context; over-context input is rejected. This supports bounding aggregate input by the model context rather than guessing from characters. The draft deliberately allocates full output separately, over-reserving overlapping capacity.
4. [Prompt caching usage accounting](https://platform.claude.com/docs/en/build-with-claude/prompt-caching): uncached input, cache reads and cache writes partition total input; creation has separate5-minute/1-hour fields when supplied. Draft settles their distinct prices; missing TTL breakdown is conservatively treated as1-hour creation. Missing token counts become unknown, never fabricated zero-cost usage.
5. [Messages API](https://platform.claude.com/docs/en/api/messages/create): max_tokens bounds output; standard_only selects standard capacity. Draft sends fixed service_tier and rejects extra request features rather than forwarding arbitrary options.
6. [PostgreSQL row locking](https://www.postgresql.org/docs/current/explicit-locking.html): conflicting row locks wait, and remain until transaction end. Draft serializes reservations through a single gate row and locks policies in fixed order. Actual multi-session contention has NOT been executed here.
