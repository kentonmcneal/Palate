# Palate passive-source research (2026-09-06)

## Q1 , Bank/card transaction scanning

**Summary.** Every aggregator returns enough to resolve a restaurant: Plaid's Transaction object carries `merchant_name`, a stable `merchant_entity_id`, `personal_finance_category` (`FOOD_AND_DRINK_RESTAURANT` etc. with a confidence level), `date`/`authorized_date`, and a `location` block (lat/lon, city, store_number) that is "typically populated only for physical retail locations"; `datetime` is available for select institutions only ([Plaid API](https://plaid.com/docs/api/products/transactions/)). Plaid refreshes an Item 1–4×/day and signals via `SYNC_UPDATES_AVAILABLE`, so a nightly `/transactions/sync` per Item costs nothing beyond the subscription ([Plaid Transactions](https://plaid.com/docs/transactions/)). No US aggregator publishes a rate card ([fintechspecs, Aug 2026](https://fintechspecs.com/blog/plaid-vs-mx-vs-finicity/)); the only public per-account numbers are Teller's and community-reported Plaid quotes.

**iOS considerations.** Plaid Link needs `react-native-plaid-link-sdk` (Expo 52+, dev build, not Expo Go) → a native build, not OTA ([npm](https://www.npmjs.com/package/react-native-plaid-link-sdk)); OAuth banks require a universal-link redirect via AASA , custom schemes "are not supported" ([Plaid OAuth](https://plaid.com/docs/link/oauth/)). Privacy label must add Financial Info → Other Financial Info and Purchases → Purchase History, linked to identity; SDK-collected data must be disclosed ([App Privacy Details](https://developer.apple.com/app-store/app-privacy-details/)). Guideline 5.1.1 requires data minimization and a privacy policy covering retention/deletion; 5.1.1(ix) says apps "that require sensitive user information should be submitted by a legal entity" , check Palate's developer account type ([Review Guidelines](https://developer.apple.com/app-store/review/guidelines/#privacy)).

**Trust.** Plaid/Harris 2025: 60% willing to share financial data; 38% rate fintechs "very trustworthy"; 84% comfortable opening fintech accounts ([Fintech Effect 2025](https://plaid.com/the-fintech-effect-report-2025/), [Money Talks](https://plaid.com/events/money-talks-consumer-survey-report-2025/)). Bank-linking for a dining app is a bigger ask than for a budgeting app; expect notable drop-off (no Palate-specific data).

**Engineering estimate (Palate).** Clone `supabase/functions/gmail-import` into `bank-import`: `connect` (link_token → public_token exchange → access_token encrypted like migration 0066), nightly cron modelled on 0051 (kill-switch + `bump_google_usage`), per-Item `/transactions/sync` with stored cursor, filter `personal_finance_category.primary = FOOD_AND_DRINK`, dedupe on (user, `authorized_date ?? date`, merchant), resolve `merchant_entity_id` → new `merchant_place_map` cache → `restaurants` name+city → Places Text Search biased by `transaction.location` or the user's last passive fix, insert into `passive_inbox` with `source='bank'`. Mobile: Plaid Link screen + AASA/universal link + settings toggle. Roughly 3–4 backend days, 1.5 mobile days, 1 day compliance (privacy label, policy, Plaid profile/questionnaire), plus a native build and Plaid approval wait: ~2 weeks calendar.

**Cost per user/month (20 restaurant txns).** Plaid ~$0.30 (reported) + Places Text Search Pro $32/1,000 = $0.032/call, first 5,000/month free ([openplacesapi](https://openplacesapi.com/blog/google-places-api-pricing)): cold cache 20 × $0.032 = $0.64; warm cache (60–80% catalogue/entity hits) $0.13–0.26. **Total ≈ $0.45–0.95/user/month, trending to ~$0.40**; $0 Plaid during Trial (10 Items) or Teller dev (100 enrollments) for TestFlight.

**Risks.** Bank data fees: JPMorgan began charging aggregators in 2025 (Plaid est. ~$300M/yr) and the CFPB reopened the fee question , aggregator prices may rise ([Payments Dive](https://www.paymentsdive.com/news/plaid-to-pay-for-jpmorgan-data-open-banking-fintechs/760192/), [Forbes](https://www.forbes.com/sites/jeffkauflin/2025/07/21/why-jpmorgan-is-hitting-fintechs-with-stunning-new-fees-for-data-access/)). Transactions post 1–3 days late and lack time-of-day for most banks, so bank hits can't drive same-evening prompts. Delivery/Uber Eats charges look like restaurants , filter by `detailed` category and known delivery merchants. Teller's 100-enrollment dev cap is consumed permanently.

**Recommendation.** Build it as a third feed behind the same confirm-inbox, but start with Plaid's Trial plan (or Teller dev) for TestFlight only, gate it behind a feature flag, and defer paid production until Places telemetry shows the catalogue hit-rate. The ~$0.30/Item Plaid number is unverified , get a written quote before modelling public-launch economics, and price in aggregator fee inflation.

## Q2 , Gmail scanning

**Summary.** `gmail.readonly` is on Google's restricted-scope list ([Restricted Scopes](https://support.google.com/cloud/answer/13464325?hl=en)), so public use requires brand verification (2–3 business days), scope justification, a demo video, a compliant privacy policy, and a CASA Tier 2 assessment from an authorized assessor, repeated every 12 months ([restricted-scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)). Google's own estimate for restricted verification is 6 weeks, "not guaranteed" ([FAQ](https://support.google.com/cloud/answer/13463817?hl=en)). Google charges nothing; the assessor does: TAC Security (Google-negotiated) $540–675 basic, $1,800 enterprise, 1–2 business-day scan, 1–3 week turnaround; others $800–1,500+ ([TAC FAQ](https://tacsecurity.com/esof-appsec-ada-casa-faqs/), [Switch Labs](https://www.switchlabs.dev/post/casa-tier-2-tier-3-security-review-providers-pricing-and-the-cheapest-option)).

| Mode | Users | What they see | Refresh tokens | Nightly cron viable? |
|---|---|---|---|---|
| Testing (External) | ≤100 listed test users | "unverified app" warning | "expire seven days from the time of consent" ([Manage App Audience](https://support.google.com/cloud/answer/15549945?hl=en)) | No , tokens die weekly |
| In production, unverified | 100 new users **lifetime**, cannot reset; then sign-in disabled ([FAQ](https://support.google.com/cloud/answer/13463817?hl=en)) | "Google hasn't verified this app" → Advanced → "Go to Palate (unsafe)" ([Unipile](https://www.unipile.com/google-oauth-100-user-limit/)) | Normal lifetime | Yes |
| Verified | Unlimited | Standard consent | Normal | Yes |

TestFlight distribution is irrelevant to Google , the cap is per GCP project. Google exempts "development, testing, or staging" apps from *submitting*, but the cap and warning still apply.

**Engineering estimate.** Code is done (gmail-import PKCE flow, encrypted tokens, review screen, 0051 cron). To go live this month: flip the OAuth consent screen to In production (unverified), uncomment `cron.schedule` in 0051, add a token-expiry alert, and record consented-user count against the 100 cap. ~0.5 day. Verification: ~1 day prep (video, policy wording, scope justification) + CASA remediation time; Palate's Supabase-hosted token store means the assessment is required (data flows through your servers).

**Cost.** Google Places per receipt as already documented in 0051; CASA $540–675/yr; ~$0 otherwise.

**Risks.** The lifetime 100-user cap is burned by beta consents and does not come back on verification, so a hard-capped beta project vs. a fresh verified project means re-consent at launch. Gmail restricted scopes require a "permitted application type"; whether receipt-parsing qualifies is **unverified** , Google may reject on use case, not security. The "(unsafe)" screen will scare some testers. gmail.metadata is also restricted, so there is no lighter-scope escape hatch.

**Recommendation.** Turn the cron on this month for TestFlight by publishing the consent screen as In production without verification, capping Gmail connects at ~60 testers to preserve headroom, and start the CASA/verification submission now so the 6-week clock runs during beta. Budget ~$675 for TAC Security. Keep Testing mode only if you accept weekly re-connects, which the nightly cron cannot.
